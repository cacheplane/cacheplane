# 0.4.1 Hotfix — Design

**Status:** Draft
**Date:** 2026-05-07
**Package:** `@cacheplane/partial-markdown`
**Target version:** `0.4.1` (patch over 0.4.0)
**Source:** Post-merge review of 0.4.0 (this session, 2026-05-07).

## Summary

Address two functional bugs and a set of test/documentation gaps surfaced by
the post-merge code-and-spec review of 0.4.0. No new features. No public type
changes (additive comments and an internal-only buffer field already exist on
`InternalState`).

## Motivation

0.4.0 shipped to npm with all 293 tests green. A subsequent multi-agent audit
compared the merged code to the original specs and found two real defects and
several test/doc gaps. None block users today (the bugs require specific
streaming-boundary scenarios), but the buffer bug in particular will surface
in real LLM streams that emit HTML mid-tag across event boundaries.

## Goals

Ship a clean 0.4.1 patch with:

1. **Functional fix:** HTML inline pending-buffer machinery actually buffers across pushes.
2. **Functional fix:** Math `\\\\(` correctly opens math (escape-parity edge).
3. **Test coverage:** fill the audit-identified gaps so CI catches regressions.
4. **Doc fixes:** README DOMPurify example, spec/CHANGELOG honesty about deferred behavior.
5. **Quality nits** that don't change behavior: clarifying comments and a couple of safe code reorderings.

## Non-goals

- New AST kinds, new node types, new parser options, new public API.
- Changes that would justify a minor (0.5.0) bump.
- Browser-validation phase work (still tracked as a separate follow-up plan).
- Image references `![alt][label]`, multi-line link-def titles, list-item link-defs
  (all explicitly deferred from 0.4.0).

## Scope — what changes

### Tier A — functional bugs

#### A1. HTML inline pending-buffer is non-functional (CRITICAL)

**Where:** `packages/partial-markdown/src/handlers/inline.ts:154-162`

**Symptom:** Mid-tag inline HTML splits across separate `push()` calls
(e.g., `parser.push('A <spa')` then `parser.push('n>B</span>\n')`) silently
drop the partial `<spa` content. The `'pending'` return path from
`matchInlineHtml` does not advance the cursor and does not buffer.
`InternalState.htmlInlinePending` exists but is never written.

**Why current tests miss it:** `chunk-boundary-html.test.ts:12-18` pushes the
chunks back-to-back within a single line; `lineBuffer` accumulates the
whole line before the inline scanner runs, so the split is invisible to
`matchInlineHtml`. A genuine multi-`push()` cross-line test would fail.

**Fix:**
- When `matchInlineHtml` returns `'pending'`, capture the bytes from `<` to
  end-of-buffer into `state.htmlInlinePending` and exit the inline scanner
  for this push.
- On the next push, prepend `htmlInlinePending` back into the inline
  scanner input and clear the field.
- Cap `htmlInlinePending` at **4096 chars** per spec. On overflow, flush
  the held bytes as a plain text node and clear the buffer.
- At `finish()`, if `htmlInlinePending` is non-empty, flush as plain text
  AND emit `'unterminated_html'` warning. (HTML spec line 343, plan line 779-787.)

**Test additions:**
- New chunk-boundary case: cross-`push()` mid-tag split arriving on a single
  inline line, but with `push()` calls returning between chunks (i.e.,
  `pushInternal` actually completes between the two halves).
- Buffer-overflow test: `<` + 5000 chars of non-tag content → flush as text,
  no hang, no infinite buffer.
- `finish()` with held buffer: emits `unterminated_html` and exposes the
  bytes as plain text.

#### A2. ~~Math `\\\\(` does not open math~~ — RESCINDED 2026-05-07

The post-merge audit incorrectly claimed `\\\\(` (four literal backslashes
+ paren) should open math. Re-reading the math design spec
(`docs/specs/2026-05-07-math-design.md`, "Detection — bracket family"):
"`\\` escapes a literal backslash so `\\(` is *not* a math opener — only
an unescaped `\(`."

Counting parity for the disputed inputs (in literal characters, not
JS-source escapes):

| Input chars | Interpretation | Math? | Current behavior |
|---|---|---|---|
| `\(` | bare `\(` opens math | ✓ | ✓ |
| `\\(` | escaped backslash + bare `(` | ✗ | ✓ matches |
| `\\\(` | escaped backslash + `\(` opener | ✓ | ✓ matches |
| `\\\\(` | two escaped backslashes + bare `(` | ✗ | ✓ matches |

The current implementation is correct per spec. **No fix needed.** This
section is retained as a record of the audit error.

### Tier B — important spec/test gaps

#### B1. Math provider tests have OpenAI ↔ Gemini delimiters swapped

**Where:**
- `packages/partial-markdown/src/__tests__/provider-openai.test.ts:177-189`
- `packages/partial-markdown/src/__tests__/provider-gemini.test.ts:93-115`

Spec (`docs/specs/2026-05-07-math-design.md`, §Validation) requires:
- OpenAI test → `\(..\)` and `\[..\]` (GPT-style)
- Gemini test → `$..$` (Gemini-style)
- Anthropic test → `$..$` and `$$..$$` (Claude-style) — already correct

**Fix:** Swap the test fixtures to match the spec's per-provider delimiter
conventions. No production change.

#### B2. HTML XSS test missing `<img onerror=...>` payload

**Where:** `packages/partial-markdown/src/__tests__/chunk-boundary-html.test.ts:45-54`

Plan called for both `<script>alert(1)</script>` (kind-1) and
`<img src=x onerror=alert(1)>` (kind-6). Only the first is tested. Kind-6
exercises a different close path (blank line vs. matching close tag).

**Fix:** Add the `<img>` payload assertion. Verify `raw` contains the
`onerror` attribute exactly as authored (so a downstream sanitizer can
strip it).

#### B3. HTML README missing DOMPurify code example

**Where:** `packages/partial-markdown/README.md` (HTML security section,
~lines 311-315).

Spec mandates a code example. README has prose only.

**Fix:** Add the example block:

```ts
import DOMPurify from 'dompurify';

if (node.type === 'html-block' || node.type === 'html-inline') {
  return <div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(node.raw) }} />;
}
```

Plus a sentence on the alternative: render escaped text instead of HTML for
untrusted streams.

#### B4. Math currency end-to-end coverage

**Where:** `packages/partial-markdown/src/handlers/math.test.ts` (or new section in `chunk-boundary-math.test.ts`).

Today, `$5` / `$ x$` / `a$b$` are tested at the **unit** level on
`isMathOpenerAt`. No paragraph-tree assertion verifies that the strings
`It costs $5.`, `Items: $5, $10`, `Items: $1.50 and $2.99` parse as plain
text with NO `math-inline` children.

**Fix:** Add E2E paragraph-tree assertions for these strings.

#### B5. Math chunk-boundary closer-adjacency

**Where:** `packages/partial-markdown/src/__tests__/chunk-boundary-math.test.ts`

Spec table (`docs/specs/2026-05-07-math-design.md`, "Chunk boundary cases")
includes `$x ‖ $` (closer preceded by whitespace → adjacency rule #3
fails → tentative match flushed as plain text). Not currently tested.

**Fix:** Add the case. Assert paragraph-tree contains text and no
`math-inline` node.

#### B6. Math in non-paragraph inline contexts

Spec requires verification that math IS parsed inside link text, table
cells, list items, and blockquotes. None of these are currently covered in
the math test files.

**Fix:** Add cases to `math.test.ts` (or `chunk-boundary-math.test.ts`)
covering each.

#### B7. Math inline streaming-arc deferral undocumented

**Where:** `docs/specs/2026-05-07-math-design.md`,
`packages/partial-markdown/CHANGELOG.md`, README.

Inline math nodes are born `complete` (line-buffered) rather than
streaming `streaming → complete` per spec section "Streaming semantics".
This is an intentional simplification; it just isn't called out anywhere.

**Fix:** Update the spec with an "Implementation note" subsection
explaining the deferral, and add a Limits-style entry to the README.
No code change.

#### B8. HTML kind-2 chunk-split test

`<!-- com ‖ ment -->` was listed in the spec/plan but only covered indirectly
in `provider-anthropic.test.ts`. Add it to `chunk-boundary-html.test.ts`.

#### B9. HTML inline tests for non-paragraph contexts

Spec required tests for inline HTML inside link text and table cells, and a
negative test for HTML NOT parsed inside code spans / code blocks. All three
absent.

**Fix:** Add three test cases.

#### B10. Link-refs chunk-boundary partition equivalence

`chunk-boundary-link-refs.test.ts` doesn't exercise `representativePartitions`.
The link-ref sample in `chunking-properties.test.ts` partially covers this,
but the chunk-boundary file should have its own.

**Fix:** Add a partition-equivalence test using the existing helper.

#### B11. Link-refs `unused_link_def` negative test

No test asserts the warning is **absent** when a def is referenced (the
interesting boundary given the empty-array-sentinel logic).

**Fix:** Add: ref → def → finish → assert no `unused_link_def` warning.

#### B12. Link-refs angle-bracket URL test

`[foo]: <https://example.com>` form is supported by the regex but never tested.

**Fix:** Add a test with the angle-bracketed form, verify URL captured
without the angle brackets.

### Tier C — quality nits (no behavior change)

#### C1. `linkRefIds` empty-array sentinel comment

**Where:** `packages/partial-markdown/src/handlers/block.ts` (`liftLinkDef`,
end of forward-resolution branch) and
`packages/partial-markdown/src/handlers/inline.ts` (matching site).

Add a comment explaining: "Empty-array sentinel marks 'this label was
referenced'. `unused_link_def` checks key presence, not array length."

#### C2. Math `$$` branch checks `isEscaped` first

**Where:** `packages/partial-markdown/src/handlers/math.ts` — `isMathOpenerAt`

Today: `if (s[i+1] === '$') return { kind: '$$' }` runs before the
`isEscaped` guard. Currently safe due to upstream filters, but fragile.

**Fix:** Move the `isEscaped` check above the `$$` short-circuit. Add a
test for `\$$` → no math.

#### C3. HTML `htmlKind` field rename — sync the spec

**Where:** `docs/specs/2026-05-07-html-design.md:92`

Spec says `kind: 1..7`; implementation uses `htmlKind: 1..7` to avoid
collision with the AST discriminant `kind`.

**Fix:** Update the spec to `htmlKind` and add a sentence explaining the
rename. (No code change.)

#### C4. HTML kind-6 tag-list assertion

`html.test.ts:79-84` only spot-checks `div`, `table`, `ul`. A typo in any
of the other 59 tags would not be caught.

**Fix:** Add an assertion that the full 62-tag set is present, e.g., compare
to a snapshot of the canonical CommonMark list.

#### C5. `value-updated` event lacks `delta` on link/citation resolution

**Where:** `packages/partial-markdown/src/parser.ts` — link-reference and
citation-reference sync paths.

When `resolved` flips, a `value-updated` event fires with no `delta` field.
Inconsistent with text deltas.

**Fix:** Document this in the `ParseEvent` JSDoc — `delta` is undefined for
non-text value-updated events. (No behavior change. Optional: add a unit
test asserting `delta === undefined` on a citation-resolution event.)

#### C6. `appendMathDisplayLine` line counter

**Where:** `packages/partial-markdown/src/handlers/math.ts:86, 91`

Increments `state.line` in both close and continue branches, but
`handleBlockLine` may already increment. Verify and add a comment, or fix
if double-counting confirmed.
